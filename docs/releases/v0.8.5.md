# Gilbert Codex v0.8.5

v0.8.5 is the official-product readiness build. It takes the work that started in the public/community line and moves the private product branch into the shape users need: cloud sign-in, isolated account data, hosted subscriptions, a real free tier, a Plus trial, private release builds, website downloads, and signed in-app updates.

This is not just a docs bump. The important change is that Gilbert Codex no longer expects a normal user to install Docker, clone a local subscription runtime, or understand the public repo structure just to use the product. Official builds point at cloud services. The desktop app still keeps local workspace control and review boundaries, but billing, account state, hosted 9Router routing, and release delivery now have production paths.

## Release Shape

- Version: `0.8.5`
- Product line: private official repo, `GilbertCodex-Official`
- Public/community line: stays frozen as the community baseline unless we intentionally publish more source there
- Website download surface: `https://gilbertcodex.com/#download`
- Updater feed: Firebase Storage `releases/latest.json`
- Release source: GitHub Actions builds Windows, macOS, and Linux artifacts, then mirrors public release files into Firebase Storage on tag releases

## What Changed

### Accounts And Isolation

Gilbert now treats authenticated users as separate tenants instead of sharing local subscription state between accounts. Firestore user documents, billing customer records, and user-owned Storage paths are scoped by Firebase UID. The desktop client can create or update normal user data, but server-owned billing fields are protected by Firestore rules so a client cannot grant itself Plus or Pro.

Storage rules now keep user files private while allowing public reads only under `releases/**`. That public release path is for installers, checksums, signatures, the website manifest, and the Tauri update feed. Everything under `users/{uid}/...` remains owner-only.

### Stripe Billing

The billing gateway is now a Cloud Run service that talks to Stripe with secrets stored outside the desktop bundle. It handles:

- Billing status reads for the signed-in Firebase user
- Stripe Checkout session creation for Plus and Pro
- Stripe Customer Portal sessions
- Webhook verification
- Subscription sync back into Firestore
- Customer mapping in `billingCustomers/{uid}`

Plus starts with a 30-day trial. The trial is configured on the Stripe subscription payload, not only in UI text, so Stripe owns the trial clock and converts the subscription to normal Plus billing after the trial period. Pro keeps normal paid checkout with no trial.

### Free Tier

The Free tier is real now. Free users can use local models and the managed free OpenRouter route set, with conservative request and token limits. Paid provider routes, paid OpenRouter routes, subscription account routes, and image generation stay gated until Firestore reports an active or trialing paid subscription from Stripe or an admin grant.

The model selector and runtime checks now use the normalized billing tier instead of trusting a stale local preview. If a user signs into a new account, the app refreshes billing from Firebase and does not reuse another account's paid state.

### Hosted 9Router

Official builds no longer depend on a local 9Router install for normal subscription routing. The desktop app can point at the hosted Cloud Run 9Router gateway. The gateway verifies Firebase ID tokens, stores per-user provider route state, applies free/paid gates, and keeps the user's subscription accounts isolated.

Free Auto routing stays available for free users. Paid routes require an active or trialing paid plan. Rate limiting happens server-side so the desktop UI and the cloud gateway agree about what the account is allowed to do.

### Connected App Gateways

The product branch now includes Cloud Run deployment paths for connector gateways. GitHub, Google, and Discord can each run as their own service with OAuth secrets and bot credentials in Secret Manager. That keeps shared secrets out of the desktop app and lets one connector fail or redeploy without taking down the others.

### Desktop Updater

The app still uses Tauri's signed updater, but the endpoint has moved away from the public GitHub repo and onto Firebase Storage:

```text
https://firebasestorage.googleapis.com/v0/b/gilbertcodex-40428.firebasestorage.app/o/releases%2Flatest.json?alt=media
```

That matters because the official repo is private. A desktop install cannot depend on private GitHub release URLs. The private repo can build the release, but the installed app needs a public signed feed and public package URLs. v0.8.5 adds that bridge.

The GitHub release workflow now has a final Firebase publication job for tag releases. After Windows, macOS, and Linux artifacts are built and uploaded to the private GitHub release, the job downloads those assets, rewrites `latest.json` so update URLs point at Firebase Storage, creates a website manifest, and uploads the public files under:

```text
releases/latest.json
releases/manifest.json
releases/v0.8.5/...
```

v0.8.5 also seeds the official private line with its own updater signing key. That is the right move for the paid product branch, but it means the matching private key and password must be preserved in GitHub Actions secrets and offline secret storage. If the older public-line updater private key is ever recovered, we can decide whether a bridge release is worth doing; until then, v0.8.5 is the clean OTA starting point for official installs.

Manual workflow dispatches still create reviewable draft releases. Tag pushes are the path that publishes public download/update files.

### Website Download Flow

The website is being moved away from live public GitHub release API reads. That API is the wrong source once the official repo is private. The website should read the Firebase Storage release manifest instead, then render platform download buttons from the same public files used by the updater.

This keeps the website and desktop updater pointed at the same release source. When the `v0.8.5` tag release finishes and Firebase Hosting is deployed, users should be able to download the latest Windows, macOS, and Linux packages from the website without needing GitHub access.

The release also publishes updater bundles, `.sig` files, `.sha256` files, `latest.json`, and `manifest.json`. The updater feed uses inline signatures as required by Tauri, so the `.sig` files are still useful for audit/download visibility but the app verifies from the feed.

## Operator Checklist

Before calling this release live:

1. Confirm these secrets exist in the private official GitHub repo:
   - `TAURI_SIGNING_PRIVATE_KEY`
   - `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` if the key is password-protected
   - `GCP_RELEASE_SERVICE_ACCOUNT_KEY`
   - Apple signing/notarization secrets if trusted notarized macOS packages are ready
2. Push the v0.8.5 commit to `official/main`.
3. Push tag `v0.8.5` to the official remote.
4. Wait for the Release workflow to finish Windows, macOS, Linux, and `publish-firebase-release-feed`.
5. Confirm Firebase Storage has:
   - `releases/latest.json`
   - `releases/manifest.json`
   - `releases/v0.8.5/*`
6. Deploy the website to Firebase Hosting.
7. Open `https://gilbertcodex.com/#download` and confirm every platform button resolves to a public file.
8. Install v0.8.5 on Windows and use the in-app update checker against the published Firebase feed.
9. Run real-device launch smoke tests on macOS and Linux before describing those platforms as fully verified.

## Known Limits

- macOS artifacts can still be ad-hoc signed and unnotarized when Apple Developer secrets are not present. That is acceptable for internal alpha testing, but public trust improves only after Developer ID signing and notarization are configured.
- The public updater feed cannot be fully proven until a signed `v0.8.5` release has been built by Actions and mirrored into Firebase Storage.
- Linux packaging still needs real desktop QA across common distributions.
- Website downloads depend on the Firebase Storage release manifest. If the release publication job fails or the Storage rules are not deployed, the site should show a release-pending fallback instead of pretending files are ready.
